## STOP — the corpus at `f1c_ida_decompiled/` already has the tool you need

Before writing ANY new script, disassembler call, memory-read helper, or
struct-dump routine: `f1c_ida_decompiled/tools/` already has it. This project
has been built up over many sessions specifically so nobody has to re-derive
offsets, re-write a poke script, or re-figure-out how to attach a debugger.
Reinventing one of these has already wasted a full session at least once.

Concretely, before you:
- read/write live game memory → `tools/poke.py`, not a new ctypes script
- want a function's callers/callees/identity → `tools/ask.py func <addr>` or
  `tools/mod_pipeline/asm_tools.py resolve <addr>`, not manual IDA re-reading
- want to know if an offset can be safely poked → `persistence_map.jsonl`
  (already has all 4,656 vehicle offsets measured), not a fresh sweep
- want to name an unknown per-driver offset → `tools/match_values.py`
- want to check if a mod/approach was already tried → `python tools/ask.py
  findings <keyword>` from repo root — `findings.jsonl` has FACT/CONFIRMED/
  DERIVED/**DISPROVEN** entries for this exact commentary system already
- want to byte-patch the exe → `tools/patch.py` (see below), never a
  standalone patcher
- need live disassembly/breakpoints → CE bridge or x64dbg MCP tools are
  already wired up (see corpus root `tools/MCP_TOOLS.md`)
- want to swap an injected DLL without restarting the game →
  `python tools/dll_unload_signal.py <event_name>`, and **build every new DLL
  with self-eject support** (pattern in `dll/pit_exit_commentary.c`: a named
  event, `WaitForSingleObject(ev, 0)` at the top of the poll loop, and
  `FreeLibraryAndExitThread(g_hinst, 0)` after the loop breaks).
  This matters because a stale prior version stays resident and silently
  double-fires alongside a freshly injected one.
  **Do NOT unload by calling `FreeLibrary` from outside** (a
  `CreateRemoteThread` ejector, CE, or a debugger): these DLLs run an
  infinite worker loop spawned in `DllMain`, and freeing the module out from
  under that live thread **crashed the game** on the first real attempt
  (2026-07-28, `findings.jsonl` DISPROVEN; the dead `tools/dll_eject.py` is
  that mistake). Let the DLL free itself — then the last instruction touching
  the module is the unload, and there is no race.
  A DLL built WITHOUT self-eject (anything older than 2026-07-28) can only be
  removed by restarting the game. CE's `enum_modules` also fails on this
  process, so there is no external shortcut.

## The two pipelines — everything here is generated from one of two sources

**Nothing downstream is hand-edited.** Both chains regenerate; editing the
output means losing it on the next run.

```

                                                   patches/<feature>/FEATURE.md
```

## Verify eid identity in ISOLATION before wiring any trigger

Before building a DLL/trigger around an eid you got from `data/full_event_dump.json`
(low-eid twin, high-eid table entry, wherever it came from), fire that exact eid
alone with `tools/commentary_inject.py` (`inject_event(eid)`, game running, no
other logic involved) and get the human to confirm out loud what actually
played. Do this BEFORE writing the trigger condition, not after.

**Why:** 2026-07-28, `dll/pit_exit_commentary.c` v1/v2 shipped with
`EID_PIT10_GO=44` and `EID_PIT12_LIMITER=42` — both wrong, one column off in
`data/full_event_dump.json`'s (low_eid, score, sdt_index) tuple (42 was
PIT12's `sdt_index`, not its eid; 44 was PIT09's twin, not PIT10's). The DLL
compiled clean, injected clean, the queue-head readback even confirmed the
eid landed — every mechanical check passed. The bug only surfaced because the
user reported "heard GEAR" instead of "Go", twice, across two separate real
pit stops. Isolated single-eid tests afterward (`inject_event(44)` → "Gear",
`inject_event(45)` → "Go", `inject_event(43)` → confirmed "Limiter Off")
found and fixed it in three calls, no DLL rebuild-and-drive-to-pits cycle
needed. Same root cause as the QUAL28/29/30 dead end earlier the same day
(eid 306 fired clean, queue accepted it, and it was still the wrong clip) —
a clean firing/queue-accept signal proves the PIPELINE works, it does not
prove you named the right eid.

**How to apply:** any time a new eid is sourced from a lookup/twin/table
match rather than live-observed (poke.py `watch`, Frida hook catching a real
call), isolation-test it first. Skip this step only for eids you've already
watched fire live and matched to a specific audible line.

## Registering a code change: patch, not prose
- Any fix that's a static byte/constant flip (thresholds, cooldowns, guard
  bytes) → register it in `patches/manifest.json` via corpus root
  `tools/patch.py add <name> <VA> "<new bytes>" --desc "..."`. This only
  RECORDS the patch (reads+verifies original bytes) — it does not touch the
  exe. Batch-apply everything at once, later, with `tools/patch.py apply <name>`.
- Then run `python tools/build_pack.py build`. That turns the registered bytes
  into `patches/<feature>/source.c` — a DLL that makes the SAME writes into the
  running process at attach. **That is the shipping format.** The pack must
  never require a modified .exe: this is a mod for other people's games, not a
  patched copy of ours. `manifest.json` stays development-only (it hardcodes one
  developer's exe path).
- A new feature needs an entry in `build_pack.py`'s `FEATURES` table naming the
  clips it restores and the evidence it works. The tool cross-checks that claim
  against `progress.json` and complains if a "RESTORED" feature's clips aren't
  DONE — don't silence that, fix whichever side is wrong.
- Do NOT apply patches to the exe per-session unless explicitly asked. The
  project's convention here is: accumulate verified patches, ship them together.
- Any fix that needs per-frame logic (a new commentary emitter, a state
  tracker) → needs a DLL tick-hook, not a manifest entry. See root
  `MODDING_PLAYBOOK.md` and `mods/grid_reorder/gr28.c` for the proven skeleton.
  If it hooks the SAME tick site as another feature already in this folder's
  TODO, it must share one DLL/hook — don't stack two redirects on one call site.

## Work queue index mapping — CRITICAL: "work queue N" = SDT index N

When user says "work queue 53", the answer is the clip at **SDT index 53**
in `PC_RE_MAIN.SDT`. Do NOT compute filtered-WQ ordinal position. The user
reads the SDT index column directly. SHIPPED clips at intervening indices
are invisible in the voice browser's work queue panel, but they still occupy
their SDT index numbers — so "work queue 9" skips SDT 1-8 (all SHIPPED) and
lands on SDT 9 (QUAL29).

**To resolve "work queue N":** parse `PC_RE_MAIN.SDT` in sequential index
order (0, 1, 2, ...), look up index N, and read the clip name + progress
status. That is the correct answer. The filtered position (skipping SHIPPED)
is an internal detail the user never sees or uses.

Example — first 11 SDT indices:
```
SDT  0 [SILENT]  PWS_QUAL32      ← work queue 0
SDT  1 [SHIPPED] PWS_QUAL07      ← invisible in WQ panel
SDT  2 [SHIPPED] PWS_QUAL02      ← invisible
...
SDT  8 [SHIPPED] PWS_QUAL23      ← invisible
SDT  9 [SILENT]  PWS_QUAL29      ← work queue 9
SDT 10 [SILENT]  PWS_QUAL28      ← work queue 10
```

Verified: WQ 0=QUAL32, WQ 9=QUAL29, WQ 10=QUAL28, WQ 53=2001_80.

- Thresholds are ESTIMATED — adjust if game uses different ranges
- Returns `{active_count, firing: {QUAL28, QUAL29, QUAL30}}`

**Known vehicle-struct offsets used:**
- +0x32C8: int32, active flag (-1=inactive, 0=player, 1=AI)
- **+0x4060: int32, LIVE RACE POSITION, 1-indexed** — the real one. Proven
  2026-07-31: sorting all 22 live cars by race distance (lap number +0x403C,
  then lap distance +0x4044) reproduces it exactly, 1..22, lapped cars included.
- +0x32D0: int32, **NOT a position — it is the SLOT INDEX and it is static.**
  Read across the grid it returns exactly i for slot i, every car, every sample.
  Two consumers were built on the wrong assumption (`check_front_row.py`, and
  `pace_probe.c` for two sessions), and because the value never changes, a
  "position unchanged" measurement taken from it is vacuous rather than merely
  wrong. `findings.jsonl`: `f1c-race-position-is-4060-not-32d0`.
- +0x4620: ASCII string, driver name (e.g. "Michael Schumacher (2001)")

## PWS vs TV — two audio systems, one controller

The game has TWO commentary audio systems sharing the same controller
(`0x5EA618`):

| System | Lookup table | SDT file | Path format |
|--------|-------------|----------|-------------|
| PWS (race engineer) | `word_5BEBB0[score]` | `Pws/PC_RE_MAIN.SDT` | `%spws%s_` |
| TV (broadcast) | `word_5BF2F8[score]` | `Tv/PC_TV_MAIN.SDT` | `%stv%s_` |

Both tables are identity-mapped at low scores `[0]=0, [1]=1, [2]=2...` (verified
live). The score→SDT-index lookup (`sub_411A00`) is called ONLY by
`FontRenderingPrep` — it drives on-screen captions, NOT audio playback. The
actual audio loading uses a different mechanism.

**File path builder:** `sub_414600` builds BOTH PWS and TV file paths in one
call, storing results at `this+0..this+63` (8 path buffers). Calls
`DriverNameIDLookup` internally with `isTv=0` for PWS paths and `isTv=1` for TV.

**The injection channel selection (SOLVED, CONFIRMED):** `sub_4119D0` picks
PWS vs TV purely by eid range on the queue entry: `1 <= eid < 291` → PWS
(`PC_RE_MAIN.SDT`), `292 < eid < 536` → TV (`PC_TV_MAIN.SDT`), 291/292 dead
gap. `commentary_inject.py` originally tested eids 293/294 (TV range by
construction, not a bug). **Inject an eid in 1-290 to get PWS audio.** Full
derivation: `docs/HANDOFF_2026-07-27_commentary_injection_tv_vs_pws.md`.
