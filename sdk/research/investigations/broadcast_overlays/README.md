## Verified findings

- The owner's key 3 observation is consistent with the native broadcast toggle. Raw `sub_4D8450` (`0x004D8450`) iterates input action codes, treats code 4 as a flip of `dword_7CF638`, clears an active display on the off branch, and queues the localized `Broadcast Displays Off` or `Broadcast Displays On` text through `TextLineWrappingAndRendering` (`0x0045BD10`). The code proves the action-code branch; the physical key-3 binding is owner-observed, not mapped by this static trace. `PlayerOptionsInitializer` (`0x004AA270`) also registers a `Broadcast Overlays` graphic-option string. The old SDK's label `AuthorizationBypassFlag` for `dword_7CF638` is misleading here; the raw toggle and `sub_4D8760` use it as a display gate.
- `GamePostMainLoop` calls `ShortComputation_f070` (`0x0049F070`), which calls both the message/toggle manager `sub_4D8450` and the on-screen HUD path `sub_49D070`. The screenshot therefore contains multiple cooperating native UI paths, not a single editable dialog texture.
- The top-left current/gap panel has a static render path: `sub_49D070` -> `sub_49D5D0` -> race case `sub_49D700` for session type 7. `sub_49D700` formats several lines and passes them to `StringFormatAndRender` (`0x0049F6A0`); `sub_49D5D0` draws a clipped backing rectangle. `sub_49C370`/`sub_49C4E0` format time or lap-count differences using `LapTimeGapCalculation` (`0x0049B6D0`). This supports the screenshot's `R. ZONTA: -2 LAPS` example. It does **not** establish that these functions draw the bottom left/right classification list.
- The ordinary warning/status text path is different. `TextLineWrappingAndRendering` bounds a line at 79 characters, word-wraps it, maps a color code and submits each line through `UtilityFunction_b9c0`. Penalty and session handlers call it. `HUDFlagRendererMain` (`0x004D82D0`) separately assembles flag glyphs and renders them through `sub_553070`. Treating the broadcast classification as an existing mod-writable alert box is unsupported.
- Race HUD resources include screen-scaled quads. `RaceInitWithConstants` (`0x004D8220`) initializes types 1–5 through `sub_4D8CF0`; type 3 constructs a `HUD 512 64.TGA` path and loads a Direct3D texture. The loose `F1 Challenge V10/SeasonData/Vehicles/hud broadcast.tga` is a 512×16 RGBA border/strip image on inspection, but no source reference proves it is the screenshot's bottom leaderboard. Its existence alone does not identify the render path.

## Screenshot interpretation and limits

The owner screenshot shows a lower two-sided classification with yellow position boxes, white abbreviated driver names and yellow numeric gaps, while the top-left panel shows the viewed driver's relative lap gap. The owner reports that drivers populate the lower list on start/finish crossing and that pressing 3 hides Broadcast Overlays. Those behaviors are **owner observations**; this investigation did not capture before/after frames or locate the lower list's authoritative event producer and draw function. Existing race-order research shows car position at `+0x4060` and finish-line race time at `+0x4098`, but their use by this particular graphic has not been traced. The lower numbers should not yet be specified as “gap to leader” from static evidence alone.

## Implication for Safety Car HUD work

The current Safety Car mod uses native timed message slots, as documented in the [HUD audit](../../../development/mods/full_safety_car/trials/2026-09-23_session_reentry_crash/HUD_AUDIT_2026-09-23.md). These are separate from the native broadcast timing/classification presentation. The broadcast layer provides a useful visual model for future race-control presentation, but no reviewed ownership, insertion API, or visibility acknowledgement for its classification rows was found. The immediate HUD wording/priority fixes should therefore stay within the established message interface. A later overlay feature would need its own specification and native toggle/texture/row lifecycle validation.
